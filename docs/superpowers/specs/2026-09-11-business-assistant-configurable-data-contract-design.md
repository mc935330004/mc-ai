# Business Assistant 可配置数据契约与项目期间关联设计

## 1. 文档状态

- 状态：待用户评审
- 对应阶段：TASK20 功能补全设计
- 适用模块：`ai-agent`
- 当前仅完成设计，不代表代码已经实现

## 2. 背景与目标

当前业务助手已经具备项目、人员、出差、打卡、报销、报告快照等基础编排能力，但出差、打卡、报销等外部业务系统尚未提供正式数据。为了避免后续每增加或调整一个接口都重新发布 Java 服务，本方案复用现有的能力注册、READ 工作流、字段字典和报告数据集配置，由管理员完成接口与字段映射，Java 代码只负责稳定的数据契约、权限编排、关联判断、统计和报告生成。

本阶段目标：

1. 支持“查询某人在某项目期间的出差、打卡、报销信息”。
2. 项目和人员分别进行权限校验，不根据角色名称在本地推断权限。
3. 项目期间从项目基础信息中取得，模型不得自行生成日期。
4. 区分项目直接关联、项目人员期间关联和无法判断三种情况。
5. 数据源未配置时返回友好提示，不生成无意义的空白报告。
6. 部分模块可用时允许生成部分报告，并明确说明缺失模块。
7. 后续仅配置已注册的 READ 工作流、入参和字段映射，不因接口参数差异修改核心编排代码。

## 3. 非目标

本设计不包含以下内容：

- 不实现或伪造外部 PM、出差、考勤、请假、报销业务数据。
- 不实现部门维度导出。
- 不新增插件系统、消息队列、微服务或通用规则引擎。
- 不兼容尚未正式使用的旧版业务助手协议。
- 不把缺失金额、缺失日期或缺失关联字段当作 `0`。
- 不允许模型猜测项目期间、员工工号、项目编码或业务金额。

## 4. 总体方案

采用“稳定语义契约 + 可配置 READ 工作流”的方式：

```text
用户请求
  -> 意图识别
  -> 人员主体解析与授权
  -> 项目主体解析与授权
  -> 查询项目基础数据并取得项目期间
  -> 查询人员与项目成员关系
  -> 按已配置的数据集执行出差、打卡、请假、报销查询
  -> 标准化安全事实
  -> 判断记录与项目的关联类型
  -> 确定性统计
  -> 对话回答
  -> 满足条件时创建并导出报告
```

模型只负责识别用户意图和组织自然语言，不参与权限判断、字段计算和关联推断。

## 5. 可配置数据集角色

数据集角色表达稳定的业务语义，不绑定具体接口名称或工作流编码。管理员从已经注册的 READ 能力中选择工作流，并为每个数据集配置不同的入参和字段映射。

| 数据集角色 | 用途 | 典型查询条件 |
| --- | --- | --- |
| `PROJECT_BASE` | 查询有权访问的项目基础信息和项目期间 | 项目编码、名称、项目经理、年度、分页参数 |
| `PROJECT_MEMBER` | 查询人员与项目的任职或成员关系 | 项目编码或项目 ID、员工工号 |
| `TRAVEL` | 查询出差记录和出差金额 | 员工工号、开始日期、结束日期、分页参数 |
| `ATTENDANCE` | 查询打卡记录，并结合请假等数据判断缺勤 | 员工工号、开始日期、结束日期、分页参数 |
| `LEAVE` | 查询请假记录，作为考勤分析依据 | 员工工号、开始日期、结束日期、分页参数 |
| `REIMBURSEMENT` | 查询报销记录和金额 | 员工工号、开始日期、结束日期、分页参数 |

约束：

- 工作流编码不写死在 Java 代码中。
- 每个数据集独立配置入参映射，允许接口必填项不同。
- 列表接口由工作流配置补齐分页编码等必填参数。
- 详情接口可以使用 ID、项目编码或其他映射后的字段。
- 所有执行都必须携带当前登录人的安全上下文，由业务系统最终判定可见数据。

## 6. 标准事实契约

外部接口字段通过字段字典转换为以下标准字段。字段名使用驼峰形式；映射来源可以不同，但语义必须一致。

### 6.1 项目基础事实

事实编码：`project_base`

| 字段 | 必填性 | 说明 |
| --- | --- | --- |
| `projectId` | 条件必填 | 与 `projectCode` 至少存在一个 |
| `projectCode` | 条件必填 | 与 `projectId` 至少存在一个 |
| `projectName` | 可选 | 仅用于安全展示 |
| `projectStartDate` | 项目期间查询必填 | 项目开始日期 |
| `projectEndDate` | 项目期间查询必填 | 项目结束日期 |

### 6.2 项目成员事实

事实编码：`project_membership_records`

| 字段 | 必填性 | 说明 |
| --- | --- | --- |
| `employeeNo` | 必填 | 人员工号 |
| `projectId` | 条件必填 | 与 `projectCode` 至少存在一个 |
| `projectCode` | 条件必填 | 与 `projectId` 至少存在一个 |
| `rosterStart` | 必填 | 在项目中的开始日期 |
| `rosterEnd` | 可选 | 为空表示当前仍在项目中 |

### 6.3 出差事实

事实编码：`travel_records`

| 字段 | 必填性 | 说明 |
| --- | --- | --- |
| `recordId` | 推荐 | 用于去重和追踪，不向模型暴露原始内部 ID |
| `projectId` | 可选 | 用于直接关联 |
| `projectCode` | 可选 | 用于直接关联 |
| `startAt` | 必填 | 出差开始时间 |
| `endAt` | 必填 | 出差结束时间 |
| `approvalStatus` | 必填 | 审批状态 |
| `amount` | 可选 | 出差金额；缺失时保持未知，不记为零 |

### 6.4 打卡事实

事实编码：`punch_records`

| 字段 | 必填性 | 说明 |
| --- | --- | --- |
| `recordId` | 推荐 | 用于去重和追踪 |
| `projectId` | 可选 | 用于直接关联 |
| `projectCode` | 可选 | 用于直接关联 |
| `time` | 必填 | 打卡时间 |

请假数据通过 `LEAVE` 数据集独立查询，不把请假字段强行塞入打卡记录。考勤分析服务只在查询完成后，按日期合并打卡、请假、排班或工作日历事实。

### 6.5 报销事实

事实编码：`reimbursement_records`

| 字段 | 必填性 | 说明 |
| --- | --- | --- |
| `recordId` | 推荐 | 用于去重和追踪 |
| `projectId` | 可选 | 用于直接关联 |
| `projectCode` | 可选 | 用于直接关联 |
| `occurredAt` | 必填 | 报销业务发生时间 |
| `requestedAmount` | 可选 | 申请金额 |
| `approvedAmount` | 可选 | 审批金额 |
| `paidAmount` | 可选 | 实付金额 |

报告中的“报销总金额”必须明确采用哪一种金额口径，默认优先使用实付金额；实付金额缺失时不得自动改用审批金额或申请金额。

## 7. 意图与会话上下文

### 7.1 意图字段

在业务意图中增加最小字段：

```text
projectPeriodRequested: boolean
```

它仅表达用户是否要求“按项目期间”查询。模型不得输出项目开始、结束日期；日期必须来自已授权的 `PROJECT_BASE` 数据集。

### 7.2 双主体上下文

会话需要分别保存：

- 当前人员选择令牌和安全展示信息。
- 当前上下文项目选择令牌、项目编码和安全展示信息。
- 已确认的查询时间范围或项目期间安全快照引用。

人员与项目不得共用同一个主体字段。追问“他的报销金额”“这个项目期间的打卡缺失”等请求，分别继承上一轮已确认的人员和项目上下文。

当用户明确输入新的人员、项目或时间范围时，新值覆盖对应上下文，不清空另一个仍然有效的主体。

## 8. 权限与主体解析

### 8.1 人员权限

- 普通员工只能查询自己的业务记录。
- 管理员或特殊角色可以通过已授权的人员列表，按工号查询他人记录。
- Java 代码不根据角色名称自行决定权限，只消费权限服务或业务系统返回的授权结果。

### 8.2 项目权限

- “我的项目”表示当前登录人有权查看的全部项目，不等同于项目经理字段等于本人。
- 用户可以按项目名称、项目编码、项目经理和年度缩小范围。
- 管理员可能拥有超过 200 个项目，禁止一次性逐项目展开全部模块查询。
- 多项目结果必须先分页展示项目摘要，并提示用户选择或缩小范围；只有明确到单个项目后，才查询合同、概算、现金流、产值或人员业务数据。

### 8.3 独立授权

人员和项目分别解析、分别授权。即使用户有权查看某个人，也不表示其自动有权查看某个项目，反之亦然。任一主体未授权时，不执行后续相关工作流，也不泄露主体是否真实存在。

## 9. 项目期间取得规则

当 `projectPeriodRequested=true` 时：

1. 必须先明确并授权一个项目。
2. 执行 `PROJECT_BASE` 数据集取得 `projectStartDate` 和 `projectEndDate`。
3. 两个日期都存在且合法时，作为后续业务数据集的查询范围。
4. 任一日期缺失、格式错误或开始日期晚于结束日期时，停止项目期间查询并返回友好提示。
5. 用户显式指定其他日期范围时，以用户明确范围为准；项目期间仅用于用户说“项目期间”但未指定日期的情况。

友好提示示例：

> 已定位项目和人员，但当前项目基础数据未提供完整的起止日期，暂时无法按项目期间查询。请补充日期范围，或联系管理员完善项目基础数据映射。

## 10. 项目关联分类

复用并收敛现有的项目记录关联服务，使它只负责关联分类，不负责金额计算。

### 10.1 `DIRECT`

业务记录存在非空的 `projectId` 或 `projectCode`，并与当前项目一致。该记录可以进入项目维度统计。

### 10.2 `PROJECT_PERSON_PERIOD`

业务记录没有项目标识，但同时满足：

1. 当前人员存在已授权的项目成员关系。
2. 成员关系与查询项目一致。
3. 成员关系时间和项目期间有交集。
4. 业务记录发生时间位于项目期间和有效成员关系期间内。

这类记录仅表示“人员在项目期间发生”，不能证明费用或行为直接属于该项目，因此只能作为上下文展示，不计入项目直接关联金额或次数。

### 10.3 `UNKNOWN`

缺少项目标识、发生时间或成员关系，无法可靠判断。记录不计入项目统计，并在回答中说明“关联关系无法确认”。

### 10.4 冲突处理

- 记录携带项目标识但与当前项目不一致时，视为无关记录，不降级为期间关联。
- 直接关联优先于人员期间关联。
- 关联分类不改变原始金额字段，也不补造缺失金额。

## 11. 确定性统计规则

统计由 Java 服务完成，不由模型计算：

- 出差次数：统计符合审批状态规则且通过关联筛选的出差记录数。
- 出差总金额：只累加口径明确且非空的 `amount`。
- 报销总金额：按明确选定的金额口径统计，默认 `paidAmount`。
- 打卡缺失：按照工作日历或排班，扣除有效请假后判断；如果工作日历或排班未配置，只展示打卡事实，不声称某天缺勤。
- 重复记录：优先按 `recordId` 去重；没有稳定标识时不得使用可能误删合法记录的模糊去重。

任何未知字段都必须保持未知，并在结果中说明数据口径或缺失情况。

## 12. 数据源可用性与友好提示

每个数据集独立判断以下状态：

- 已配置并成功返回数据。
- 已配置且查询成功但没有记录。
- 未配置。
- 无权限。
- 执行失败。

### 12.1 全部不可用

如果用户请求的所有业务模块都未配置、无权限或执行失败，且没有任何成功的有效章节：

- 返回友好提示。
- 不创建报告任务。
- 不生成空白文件。

提示示例：

> 当前尚未配置可用的出差、打卡或报销数据源，暂时无法生成有效报告。请联系管理员完成业务数据集、READ 工作流和字段映射配置后重试。

### 12.2 部分可用

至少一个模块查询成功时，可以生成部分回答和部分报告。未配置或失败的章节必须单独说明，例如：

> 已生成部分报告；本次出差和打卡数据可用，报销数据源尚未配置，因此未纳入统计。

### 12.3 成功但无记录

已配置的数据源成功返回零条记录是有效结果，应展示“该范围内未查询到记录”，但不得把它与“数据源未配置”混为一谈。只有这类有效空结果时，可以生成包含查询范围、数据口径和“无记录”结论的报告；它不属于无意义的空白报告。

## 13. 报告生成设计

### 13.1 生成条件

- 用户明确提出导出需求。
- 至少存在一个成功章节，包括成功返回零条记录的有效章节。
- 人员、项目和时间范围均已通过必要授权与校验。

### 13.2 报告内容

报告按用户实际请求组合章节，不固定要求合同、概算、现金流、产值、出差、打卡、报销全部存在。每个章节至少包含：

- 查询主体和范围。
- 数据来源和统计口径。
- 可用性状态。
- 确定性统计结果。
- 项目关联标签。
- 缺失或未知字段说明。

### 13.3 关联标签持久化

优先复用现有报告章节的安全提示字段和快照安全事实，不新增数据库字段：

- 直接关联章节标记“项目直接关联”。
- 存在人员期间关联记录时标记“项目人员期间关联，仅供上下文参考，不计入项目直接统计”。
- 存在未知记录时标记“部分记录的项目关联无法确认”。
- 数据源未配置时标记“数据源未配置，本章节未纳入统计”。

只保存统计结果和安全标签，不为关联判断额外持久化原始内部 ID、权限信息或接口原文。如果实际实现确认现有安全字段不能表达上述信息，必须暂停并单独说明数据库变更风险，不能擅自修改已执行的 Flyway 脚本。

### 13.4 导出格式

导出格式由用户需求决定，并复用现有报告渲染能力。不同格式共享同一份逻辑报告，不分别实现业务统计，避免出现格式间口径不一致。

## 14. 错误处理与安全要求

- 所有外部查询只允许调用已注册并启用的 READ 能力。
- 每次工作流执行都传入当前登录人的授权上下文。
- 不把角色名称、权限表达式、数据库主键或接口原始错误返回给模型。
- 未授权和不存在对外使用统一安全提示，避免枚举人员或项目。
- 单个数据集失败不影响其他独立数据集，但必须记录运行追踪并在回答中安全披露。
- 报告快照只能保存经过字段策略清洗的安全事实。
- 日志不得记录 Token、Cookie、完整身份证号、银行卡号等敏感信息。

## 15. 预计代码影响范围

实际编码前必须再次核对现有类和调用链。预计只涉及 `ai-agent` 内以下范围：

1. 业务意图 DTO、解析器和校验器：增加“按项目期间”意图。
2. 会话上下文：分离人员主体和项目主体。
3. `BusinessAssistantService` 编排：增加项目期间、成员关系和数据集可用性流程。
4. 项目记录关联服务：输出 `DIRECT`、`PROJECT_PERSON_PERIOD`、`UNKNOWN` 分类。
5. 出差、打卡、请假、报销确定性统计服务：消费标准事实，不直接调用数据库。
6. 报告计划、快照和渲染链路：传递安全的关联标签和缺失数据说明。
7. Mapper XML：只有确实存在复杂查询或统计 SQL 时修改；SQL 必须写入对应 `Mapper.xml`。
8. 单元测试、集成测试和业务验收测试。

默认不修改 `pom.xml`，不新增第三方依赖，不新增数据库迁移，不改动 `ai-common` 和 `ai-rag` 的模块边界。

## 16. 实现约束

- 使用简单的 DTO、枚举和 Service 方法完成，不新增通用规则引擎。
- Controller 仅做协议转换，业务编排留在 Service。
- 单个方法只承担一个清晰步骤，避免方法内部继续定义复杂方法套方法。
- 新增 Java 类使用中文注释说明职责、关键规则和易错点。
- 新增文件必须显式执行 `git add`。
- 不保留已被新实现替代且没有调用方的旧代码。
- 所有复杂 SQL 写入对应 `Mapper.xml`，不使用注解拼接复杂 SQL。
- 先写失败测试，再实现最小代码使测试通过。

## 17. 验收场景

实现完成后至少覆盖以下场景：

1. “查询张三在 XXXT2674040 项目期间的 6 次出差总金额、打卡缺失和报销总金额”。
2. 项目和人员都有权限，全部数据集已配置并成功返回。
3. 项目基础信息没有完整起止日期，返回提示且不继续查询项目期间数据。
4. 人员有权限但项目无权限，后续工作流不执行且不泄露项目存在性。
5. 项目有权限但人员无权限，后续工作流不执行且不泄露人员存在性。
6. 业务记录项目编码与当前项目一致，判定为直接关联并计入统计。
7. 业务记录没有项目编码，但成员关系和时间重叠，判定为人员期间关联且不计入项目直接统计。
8. 业务记录项目编码与当前项目不一致，不降级为人员期间关联。
9. 金额为空时展示未知，不变成零。
10. 出差和打卡可用、报销未配置，生成部分报告并明确缺失章节。
11. 全部请求模块未配置或不可用，返回友好提示且不创建报告任务。
12. 已配置模块成功返回零条记录，正确区分“无记录”和“未配置”。
13. 没有工作日历或排班时，不错误判断打卡缺失。
14. 报告中的统计值与对话回答使用同一套确定性结果。
15. 多于 200 个有权项目时只分页展示摘要，并提示缩小范围，不批量查询每个项目的业务模块。

## 18. 验证方式

编码完成后按影响范围执行：

```powershell
mvn -pl ai-agent -am test
mvn -DskipTests compile
```

同时执行：

- 业务助手重点验收测试。
- 权限安全矩阵测试。
- 数据集未配置和部分可用测试。
- 报告任务不生成空白文件测试。
- Flyway 校验；只有新增迁移时才验证新版本迁移。
- 检查 `git status`，确认所有新增 Java 文件均已加入版本控制。

## 19. 风险与控制

| 风险 | 控制方式 |
| --- | --- |
| 外部接口字段经常变化 | 通过字段字典映射到稳定事实契约 |
| 接口参数不一致 | 每个数据集独立配置工作流入参映射 |
| 管理员项目数量过多 | 项目列表分页，明确单项目后再展开模块查询 |
| 模型错误计算金额或日期 | Java 确定性统计，模型只负责表达 |
| 人员期间记录被误认为项目费用 | 单独标记且不计入项目直接统计 |
| 缺失数据被显示为零 | 使用未知状态和安全提示，禁止默认补零 |
| 部分模块失败导致整次请求失败 | 独立执行并允许部分结果，失败章节明确披露 |
| 未配置时生成空白报告 | 创建报告任务前执行有效章节校验 |

## 20. 完成定义

满足以下条件后，才能认为本功能完成：

- 设计中的标准事实契约已经落地并有测试保护。
- 人员和项目双主体上下文不会相互覆盖。
- 项目期间只来自授权后的项目基础数据或用户明确日期。
- 直接关联、人员期间关联和未知分类行为一致。
- 出差、打卡、请假和报销在没有真实数据时仍能正确处理未配置状态。
- 部分报告和不生成空白报告规则全部通过测试。
- 所有新增后台类有必要的中文注释并已显式加入 Git。
- 模块测试和编译通过；无法验证的外部数据部分明确列为待用户配置项。
