# 工作流问答展示、风险规则与上下文连续性设计

## 1. 背景与目标

当前工作流查询成功后主要按 `ReportSchema` 展示，适合完整报表，但不适合日常连续问答。新方案在不破坏现有报表链路的前提下，增加类似 ChatGPT 的纯文字流式回答，并确保事实完整、上下文不丢失、风险判断可追溯。

本次目标：

- 普通业务问答使用文字 SSE 流式输出，不构造 `ReportSchema`。
- 用户明确要求完整报表时，继续使用现有 `ReportSchema` 固定组件。
- 管理类查询默认先汇总，只展开风险、异常和数据不足的项目。
- 精确项目编号查询返回该项目的明确信息。
- 风险和不规范由结构化规则判定，AI 只负责解释，不负责决定事实和结论。
- 同一会话中的“这个项目”“这些风险项目”“继续分析”等追问能够稳定继承上下文。
- 在前端单页应用内切换页面或聊天会话时，正在生成的回答不中断，并允许用户主动终止。

## 2. 设计原则

1. `ANSWER` 和 `REPORT` 是两条独立展示链路，不能把文字回答包装成报表组件。
2. 后端决定事实、金额、数量、风险状态和数据完整性；AI 只能补充摘要、原因说明和建议。
3. 先返回确定性事实，再流式追加 AI 文本。模型失败不能让已查询到的数据消失。
4. 复用现有工作流、`ResultArtifact`、会话状态、模型流式调用和 SSE 协议，不增加新的通用框架。
5. 当前前端未使用 Pinia/Vuex，不为一个功能新增状态管理依赖；使用 Vue `reactive` 模块单例管理全局 AI 任务。
6. 第一版不实现浏览器刷新、关闭后重新连接和历史事件重放。

## 3. 展示模式

工作流增加一个简单的默认展示模式字段：

- `AUTO`：推荐用于新配置。根据用户表达选择 `ANSWER` 或 `REPORT`，没有明确表达时使用文字问答。
- `ANSWER`：工作流默认使用文字问答。
- `REPORT`：工作流默认使用完整报表。

`AUTO` 的判定顺序：

1. 用户本轮明确要求“生成完整报表、查看完整明细、导出报表”等，覆盖工作流默认值并选择 `REPORT`。
2. 用户本轮明确要求“简单说明、总结、有哪些风险”等，覆盖工作流默认值并选择 `ANSWER`。
3. 没有明确表达时，使用工作流配置值；配置为 `AUTO` 时选择 `ANSWER`。
4. 旧发布版本缺少该字段时按 `REPORT` 处理，保证已有报告行为不变。

展示模式只影响结果呈现，不改变工作流执行、能力调用、字段权限和安全结果。

## 4. 总体数据流

### 4.1 文字问答链路

```text
用户问题
→ 会话上下文解析
→ 工作流路由和能力执行
→ 保存安全结果 ResultArtifact
→ 提取确定性事实和项目集合
→ 执行已发布风险规则
→ 更新结构化会话状态
→ 发送 ANSWER_START
→ 发送确定性事实/汇总文本
→ 模型真实流式生成解释和建议
→ 连续发送 ANSWER_DELTA
→ 保存完整回答快照
→ 发送 ANSWER_DONE
```

文字消息只允许一个稳定的 Markdown 子集：普通段落、粗体和一级无序列表。禁止 Markdown 表格、HTML、CSS 和嵌套列表，避免不同模型产生错乱样式。

### 4.2 完整报表链路

```text
用户问题
→ 会话上下文解析
→ 工作流执行
→ ReportSchema 基础数据
→ REPORT_BASE 立即展示
→ 可选 AI 分析流式追加
→ REPORT_DONE
```

现有报表模板、区块渲染和 `ReportSchema` 协议保持不变。文字问答不得复用 `REPORT_BASE` 或报告组件。

## 5. 回答内容策略

### 5.1 管理汇总查询

当用户询问“我管辖的项目信息”等可能命中大量项目的问题时：

- 不展示全部项目列表。
- 返回项目总数、关键金额或状态汇总。
- 只列出命中风险规则的项目、数据不完整的项目以及其他明确异常项目。
- 正常项目只计入汇总，不逐条展开。
- 如果异常项目仍然很多，按严重级别和业务重要度排序并说明总数；不使用“前 5 跳”之类容易误解的说法。

### 5.2 精确项目查询

当输入包含能够唯一定位的项目编码时，返回该项目的核心事实、关键金额、命中规则及证据。用户明确要求完整明细或完整报表时再切换 `REPORT`。

### 5.3 AI 边界

- AI 输入只包含经过权限和字段策略处理的安全数据。
- AI 不得补写不存在的金额、状态、项目或风险依据。
- 后端将必须出现的事实先写入回答；AI 遗漏时不影响事实完整性。
- 模型超时或失败时，保留确定性结果，并追加“智能分析暂不可用”的简短提示。

## 6. 结构化风险规则

### 6.1 第一版配置

规则配置保持扁平、精确：

- 规则编码、名称、适用工作流、严重级别、启用状态和版本。
- 条件关系：`AND` 或 `OR`。
- 左侧字段。
- 运算符：等于、不等于、大于、大于等于、小于、小于等于、包含、不包含、为空、不为空、属于、不属于。
- 右侧类型：固定值或另一个字段。
- 右侧倍率，默认 `1`，用于表达“回款金额 < 合同金额 × 0.5”。

第一版不支持自然语言规则、任意脚本、SQL、SpEL、嵌套条件组和 RAG 判定。

### 6.2 判定结果

每条规则只能产生：

- `MATCHED`：满足风险或不规范条件。
- `NOT_MATCHED`：数据完整且不满足条件。
- `UNKNOWN`：判定所需字段缺失或无法转换。

`UNKNOWN` 不能当作无风险，回答必须列出缺失字段。没有配置规则时，只返回已知事实，并明确提示“当前未配置风险判定规则”，不能回答“没有风险”。

### 6.3 发布与审计

- 风险规则作为 `GraphSpec.riskRules` 随工作流发布快照保存，不新增独立规则表；规则版本直接使用工作流版本 ID。
- 发布前校验字段是否属于该工作流的已发布字段字典，并校验左右值类型和运算符兼容性。
- 运行时复用现有计算指标和安全结果，不绕过字段权限。
- 判定结果复用现有 `ai_run_step` 运行步骤记录，保存规则编码、工作流版本 ID、项目编码、判定状态、脱敏证据值、原因和判定时间，不新增判定结果表。
- AI 只把判定结果转换为用户易懂的文字，不改变判定状态。

## 7. 上下文记忆

上下文仅在同一聊天会话中自动继承，新建会话不自动带入旧会话业务状态。

### 7.1 两层上下文

1. 最近文本历史：保证语言连续性。
2. 结构化业务状态：保证项目、工作流、参数和风险集合不会被模型猜错。

结构化状态在现有 `BusinessConversationState` 基础上增量扩展：

- 当前工作流及版本。
- 上次规范化输入。
- 当前聚焦对象及对象类型。
- 上次展示顺序对应的对象集合。
- 风险对象集合和 `UNKNOWN` 对象集合。
- `ResultArtifact` 引用。
- 风险判定结果引用。
- 上次展示模式。
- 是否等待用户补充参数。
- 最后更新时间。

完整业务数据继续保存在 `ResultArtifact`，会话状态只保存标识、必要集合和引用，避免重复存储大对象。

### 7.2 指代解析规则

- “这个项目”：只有一个聚焦项目时自动继承；存在多个候选时必须追问。
- “这些风险项目”：使用上一轮保存的风险项目集合。
- “第一个项目”：使用上一轮稳定的展示顺序，不能重新排序后再解释。
- “继续分析”“为什么有风险”：使用上一轮 `ResultArtifact` 和风险判定引用，不重新猜测路由。
- “刷新数据”：继承已确认参数并重新执行工作流。
- “生成完整报表”：继承当前对象和参数，只切换到 `REPORT` 链路。
- 用户明确更换项目、工作流或说“重新开始”时，清除不再适用的聚焦状态。

上下文分类模型失败时，不能直接丢弃上下文。优先使用确定性指代规则；只有无法唯一判断时才追问用户。

## 8. 真实 SSE 与主动终止

现有 `AgentStreamSession.publishAnswer()` 对完整文本分块不等于模型真实流式。新链路应直接消费现有 `TrackedChatClientService.stream(...)` 返回的 `Flux<ChatResponse>`，累计完整内容的同时逐段发送 `ANSWER_DELTA`。

建议事件语义：

- `ANSWER_START`：文字回答开始。
- `FACTS`：可选的确定性事实或汇总，不依赖模型。
- `ANSWER_DELTA`：模型增量文本。
- `ANSWER_SNAPSHOT`：最终完整文字快照，用于持久化和前端校正。
- `ANSWER_DONE`：正常完成。
- `ERROR`：工作流失败等不可继续错误。

主动终止要求：

1. 前端调用后端终止接口，参数至少包含 `conversationId` 和 `runId`。
2. 后端定位当前运行任务并释放模型 `Flux` 订阅或相关任务。
3. 保留已生成的部分文字，运行状态标记为“用户已终止”，不能记录为正常完成或模型失败。
4. 后端确认终止后，前端关闭本地 SSE。
5. 单纯执行 `AbortController.abort()` 不能视为业务终止，因为后台可能继续计算和计费。

第一版使用进程内活动任务注册表保存可释放的模型订阅，不把运行对象写入 Redis。该方案适用于当前单实例部署；如果后续采用多实例部署，必须结合粘性路由或 Redis 终止通知将请求发送到实际持有任务的实例，否则不能承诺跨实例终止。

## 9. 前端跨页面任务

当前 `AiChat/index.vue` 在 `onUnmounted` 中调用 `cancelCurrentRequest()`，因此切换页面会中断请求。第一版调整为：

- 把 SSE、`AbortController`、消息增量和运行状态从页面组件移到全局模块单例。
- 使用 Vue 3 `reactive` + composable 实现，不新增 Pinia/Vuex 依赖。
- 任务主键使用 `conversationId + runId`，允许切换聊天会话后原任务继续。
- 聊天页面重新挂载时订阅同一任务状态并恢复当前增量文本。
- 应用公共区域显示轻量运行提示和“终止”入口；具体挂载位置在实施前按现有布局组件确认。
- 页面卸载只解除视图订阅，不关闭 SSE。

第一版仅保证当前浏览器标签页内的 SPA 页面切换。浏览器刷新、关闭后重开、跨标签页接管和服务端事件重放留到后续需求。

## 10. 错误处理

- 工作流或能力执行失败：不进入回答或报表生成，返回明确的普通错误消息。
- 风险规则单条配置非法：发布时阻止；不能把错误规则带入运行。
- 风险规则运行字段缺失：返回 `UNKNOWN`，其他项目和规则继续处理。
- 模型连接失败或超时：保留确定性事实和规则结论，追加降级提示并正常结束事实回答。
- SSE 客户端意外断开：第一版取消对应模型流，但已经保存的业务结果和上下文不回滚。
- 用户主动终止：保留部分结果，单独记录终止状态。
- 报表构建失败：只影响 `REPORT` 链路，不能误回退成伪装的文字报表。

## 11. 实施边界与阶段

本需求按以下阶段实施，每阶段完成后静态检查代码完整性并说明下一阶段：

1. 展示策略：增加 `AUTO / ANSWER / REPORT`，保持工作流执行不变。
2. 文字回答：确定性事实、真实模型 SSE 和受限 Markdown。
3. 前端任务管理：跨 SPA 页面继续、会话切换继续、主动终止。
4. 上下文增强：结构化状态、确定性指代和 `ResultArtifact` 复用。
5. 风险规则后台：配置、发布校验、判定、证据和审计。
6. 风险规则前端：扁平条件编辑器，不提供自然语言或脚本配置。
7. 全链路静态复核和闭环总结。

后台代码由 Codex 输出完整、可替换的代码示例并标明路径和修改位置，由用户操作项目；前端代码由 Codex 直接修改。实现中能替换的旧逻辑不叠加保留，不新增无用兼容层。

## 13. 验收标准

1. 同一工作流可以按配置和用户明确意图输出文字回答或完整报表。
2. `ANSWER` 全程不出现 `ReportSchema` 或报告组件。
3. 管理查询只汇总并列出风险、异常和数据不足项目，不平铺全部正常项目。
4. 精确项目编码查询能够展示该项目核心事实和关键金额。
5. 模型失败时，确定性事实、规则结论和上下文不丢失。
6. 没有规则时不误判无风险；缺字段时明确返回 `UNKNOWN`。
7. “这个项目”“这些风险项目”“继续分析”“生成完整报表”等追问按上一轮结构化状态执行。
8. 在应用内切换页面或聊天会话，原回答继续生成；返回后能看到最新内容。
9. 用户主动终止后，后端停止模型任务，部分回答保留，状态不是正常完成。
10. 现有 `REPORT` 报告配置、区块渲染和分析追加行为不被破坏。
11. 不新增 Pinia/Vuex、消息队列、RAG 风险判定或脚本规则引擎。

## 14. 明确不在第一版实现

- 浏览器刷新、关闭后重连与 SSE 历史事件重放。
- 跨浏览器标签页接管生成任务。
- 多实例部署下通过 Redis 协调跨实例终止。
- 自然语言自动生成风险规则。
- 由 AI 自主判断风险结论。
- 基于 RAG 的风险规范判定。
- 复杂嵌套条件、脚本、SQL 或表达式规则。
- 对所有项目逐条生成 AI 长文本分析。
